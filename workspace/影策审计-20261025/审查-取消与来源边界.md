## 实测通过的范围

新增 `character-prompt-formats/tests/audit-cancellation.test.js`，4/4通过：

1. `callbacks.signal` 在任务已创建后中止等待，没有第二次创建模型任务。
2. `e.signal` 同样可中止等待。
3. 任务查询服务失败会把异常传给调用方，不自动创建第二次模型任务。
4. `waitComplete` 将 AbortSignal 传给任务查询，不向状态回调传输 `textDraft`。

这些是注入依赖的实际函数测试；没有向供应商发送请求，没有说明供应商收到取消，没有证明桌面UI接通。

## 当前仍未完成的取消接线

- 当前安装 `chapters-CeKTBaiU.js` 的章节 `cn` 调用 `bn` 只传 `{onTaskUpdate: ...}`。没有创建 AbortController，也没有传 signal。
- 章节模块没有 `AbortController` 或 `cancelTask` 引用。生成弹窗的 `onCancel:()=>j(!1)` 是关闭弹窗；生成开始前会立即 `j(!1)`。它不是取消模型任务。
- 新 `generatePlannedChapter` 只在 `waitComplete` 使用 `callbacks.signal||e.signal`。准备Skill、策略构造与 `createTask` 之前没有检查 signal。预先取消或准备期间取消，仍可能提交一次模型任务，再在等待阶段中止。
- “中止本地等待”不能显示为“供应商已取消”。底层应分别记录取消请求、任务状态和供应商取消结果。
- 查询失败目前直接报错且释放单次提交锁。用户手动重新点击可能新建任务，原供应商任务是否仍运行需要任务历史/恢复机制判断。不能把“无自动重试”外推为“用户重试绝无重复费用”。

建议主代理在章节组件持有每章生成 AbortController，向调用传入 signal；在 prepare 和 createTask 前做取消检查；通过产品已有任务取消 API 请求后端停止任务；UI区分取消等待与已确认取消，并保留旧任务供恢复和诊断。现有任务取消API应从真实请求模块/任务页确认，不猜接口路径。
